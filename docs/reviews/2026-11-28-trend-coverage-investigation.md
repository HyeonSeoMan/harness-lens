## 구성 요소별 득실이 두 개뿐인 이유

`skills/harness-analyze/references/analysis-protocol.md:87`의 `components`는 역할이 불명확하거나 상호작용하는 요소만 최대 10개 고르라고 한다. 하지만 **이는 역할 설명 배열이며 componentTradeoffs의 개수 규칙이 아니다.** `:91`의 득실 규칙은 “득과 실이 함께 있는 구성 요소, 각 항목에 근거 1개 이상”뿐이다. 대표성·후보 전수 검토·선정 이유·생략 이유가 없다. `:114`의 6,000토큰 목표도 짧은 선택을 유도할 수 있지만 당시 생략의 직접 원인이었다고 단정하지 않는다.

`skills/harness-analyze/schemas/analysis.schema.json:984`의 componentTradeoffs 배열에는 최소 개수·전체 커버리지 제약이 없다. `engine/src/checks.mjs:35`~`:60`은 근거·구성 요소 참조의 존재만 확인한다. 반면 변경 해석에는 `:63`~`:77`의 V-CHANGE-COVERAGE가 있어 모든 변경을 다루도록 한다. 현재 구성의 득실에는 대응 규칙이 없다. `engine/src/report/client.mjs:469`~`:475`는 전달된 배열을 모두 map하므로 2개로 자르지 않는다. 기존 G절의 역할 빈칸 문제와 이 득실 개수 문제도 별개다.

따라서 **현재 계약상 두 개만 있어도 유효하지만, 충분히 검토했는지 사용자가 알 수 없는 프로토콜·설명 공백**으로 분류한다. Hook 개수는 득실 해석의 정답 개수가 아니며 서로 같은 파일을 쓰는 별도 이벤트 Hook도 있다. 현재의 9개와 과거의 10개는 동등한 기준 모집단이 아니다.

후속 프로토콜 개정안(`analysis-protocol.md` §2.2 끝·§2.3 componentTradeoffs 행):

> 인벤토리의 구성 요소를 한 번 모두 검토한다. 외부 실행·권한/검증 게이트·반복 주입·종료 차단·여러 요소의 의존 관계처럼 영향이 큰 후보를 먼저 살핀다. Hook은 이벤트와 강제 방식이 다른 후보를 각각 검토하되, 같은 스크립트·같은 동작의 중복 서술은 피한다. 후보마다 득·실 양쪽에 근거가 있는지 확인하고, 둘 다 설명할 수 있는 요소만 componentTradeoffs에 쓴다. 근거 없는 비용이나 효과를 개수 맞추기로 만들지 않는다. 조건부 영향은 추론임을 밝히고 검증 방법을 관련 finding에 연결한다.
>
> 전체를 다루지 않으면 limitations에 “주요 후보 중 양쪽 근거가 있는 요소를 선별했다”는 범위, 생략한 후보의 componentId와 사유(동일 동작 중복·한쪽 근거만 있음·근거 부족·출력 예산상 생략)를 짧게 남긴다. 수치 목표를 만족시키려고 내용을 채우지 않는다. 토큰이 부족하면 반복 표현부터 줄이고 중요한 미검토 후보를 숨기지 않는다.

현 스키마에는 구조화된 생략 목록이 없으므로 위 제안은 기존 limitations 필드로 적용 가능하다. 향후 기계 검증이 필요하면 별도 설계로 대상 ID별 `included / duplicate / insufficient_evidence / one_sided / budget_omitted` 처분을 추가하고 참조·중복·전체 검토 여부만 검사한다. gains와 costs의 “진실성”을 기계 검사로 보장하거나 최소 해석 개수를 품질 점수로 쓰지는 않는다.

프로토콜 개선 검증은 Hook만 10개 있고 서로 다른 게이트·반복 주입·종료 이벤트가 섞인 합성 인벤토리로 한다. 검토자가 각 후보의 해석 또는 생략 사유를 추적할 수 있는지, 비슷한 Hook을 중복 서술하지 않는지, 양쪽 근거가 없는 요소에 가짜 비용을 만들지 않는지, 출력 예산 안에서 중요한 미검토 후보를 밝혔는지 확인한다. 이는 LLM 결과의 내용 검토이며 기존 스키마 통과만으로 충분하다고 판정하지 않는다.

## 검증·제약

- `node --test tests/*.test.mjs`: 112/112 통과.
- `npm ci --ignore-scripts` 후 `npm run check-bundle`(engine): 통과. 최초 번들 검사에는 esbuild가 설치되지 않아 실패했으며 의존성 설치 후 해결했다. 커밋된 코드·번들은 바꾸지 않았다.
- DiceForge의 `git status --short`는 실행 후 비어 있었다. 대상의 Hook·MCP·빌드·테스트는 실행하지 않았다. 엔진 산출물과 진단 스크립트는 `/tmp`에만 두었다.
- 과거 1,309요청을 담은 원래 run·봇 매핑·당시 파일 집합은 확보하지 못했다. 따라서 당시의 정확한 요청별 차이와 득실 두 항목의 선정 동기는 미확인이다. 이번 데이터와 코드 경로로 확인한 범위는 이틀 현상의 재현, configSince·보존·badUsage 가설의 배제, 현재 window 오표기와 프로토콜 공백이다.
